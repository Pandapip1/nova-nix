# Changelog

## Unreleased

- **Substitution accepts bzip2, so historical cache paths and narinfos with no Compression field at all can be fetched.** cache.nixos.org narinfos written before the xz switch declare `Compression: bzip2`, and upstream C++ Nix reads an absent or empty Compression field as bzip2, so those paths could only ever fail here: the register named the codec in its rejection but no decoder stood behind the name. Both decompression paths - streaming and the strict oracle - now dispatch it through nova-cache 0.11's bzip2 sublibrary, bounded by the declared NarSize exactly as xz and zstd are, with stream errors retried and output past the bound refused as the served object misdeclaring; there is no decoder-memory knob to set, because bzip2 carries no attacker-chosen dictionary size and its decoder state is a small constant of the format. The empty spelling now decodes rather than rejects, completing the upstream parity the register was written for. The bound rises to nova-cache >= 0.11 && < 0.12 with the bzip2 sublibrary added to the library's set, and the pinned index-state advances past the release. 0.11 also tightens the zstd codec, which the suite now pins: a truncated frame and trailing bytes after the last frame refuse with a stream error instead of yielding a short output, so truncation is caught at the codec rather than left to the NAR grammar above it. (#115)
- **New: `--exec-wrapper SYSTEM=PATH`** - build a derivation whose `system` this machine cannot execute, by naming a launcher for it: `--exec-wrapper x86-windows=/path/to/wine` builds the PE32 chain on Linux. The launcher is prepended to the builder at the spawn boundary and never enters the derivation, so the store paths a wine-hosted build produces are the same ones a Windows host produces -- which is what makes comparing them worth anything. A derivation for the host's own platform is spawned directly whatever is configured. Verified: the whole stage0-pe32 chain, from the 181-byte PE32 seed through Mes, builds on Linux and the Mes it produces runs.
- **New: `pkgs/linux/bootstrap/gcc/latest.nix`** - GCC 15.3.0, built by GCC 10.4.0: the end of the ladder, a current compiler with every byte behind it traced to the 181-byte hex0 seed. It takes three gccs to get here because each is written in a language only the one below it can compile -- 4.6 in C for tcc, 4.6's g++ for gcc 10, and gcc 10 for this. Verified on C++20 -- concepts, ranges, the spaceship operator -- and on C23, static and dynamic.
- **New: `pkgs/linux/bootstrap/gnutar/latest.nix`** - GNU tar 1.35, compiled by gcc against musl and linked through `musl-gcc`. 1.12 was chosen for being the last tar the Mes C library can build, and it carried the bootstrap from the mescc-tools unpackers as far as a real compiler -- but it predates the pax extended headers a modern release tarball uses, and stops at gcc 15's with "Unknown file type 'x'". Three tars now, each earning its place: 1.12 under Mes's libc to get past the unpackers, 1.12 under musl to restore modification times, and 1.35 under gcc to read a current archive.
- **New: `pkgs/linux/bootstrap/gcc/10.nix`** - GCC 10.4.0, built by the 4.6.4 with C++: the first gcc here written in C++ rather than C, which is why 4.6 had to grow a g++ first. 10.4.0 rather than 10.5.0 because 10.5 does not build with a compiler this old (gcc bug 110716), and its gmp is 6.2.1, the last that 4.6 can still compile. Unlike 4.6.4 this gcc has `--with-native-system-header-dir`, so the headers are named on the command line rather than edited into the makefile, and with `--with-sysroot` it finds musl by itself: it compiles and links against this bootstrap's C library with no include or library path set at all. Verified on C++17 -- fold expressions, structured bindings, `std::optional`, `std::string_view`, `unique_ptr`, `unordered_map` -- and on C, both static and dynamic.
- **New: `pkgs/linux/bootstrap/gcc/cxx.nix`** - GCC 4.6.4 with C++, built by the GCC 4.6.4 below it. The gcc tcc built speaks only C, because that is as far as tcc could carry it; this is the same source built by that compiler, with libstdc++ and g++ -- which is what every gcc after 4.7 needs, being written in C++ itself. It links against the musl gcc built rather than the one tcc built, since libstdc++ wants a shared C library and a dynamic loader, and it names that loader on every link: the gcc below has none it can point at, so without it configure cannot run the program it just compiled. libstdc++ also picks its OS-specific configuration off the target triple and has no entry for musl, so `os/generic` is chosen over the glibc one. Verified: it compiles a program using templates, `std::map`, `std::sort` and exceptions, and every answer comes out right.
- **Fixed: a build writes into its output path, not into a temp directory it is moved out of.** `$out` is now the final store path, as upstream's is. Building somewhere else and moving afterwards looks equivalent and is not: anything that records where it was built -- a compiler driver, a libtool archive, musl's `musl-gcc.specs` -- recorded the temp path, which is deleted the moment the build ends. The bootstrap's own binutils had 27 such files and gcc had 6; gcc worked anyway only because it also resolves relative to `argv[0]`. The reference scanner could see the edge but not repair the bytes, and repairing them afterwards is not possible in general: the two paths are different lengths, so an embedded copy cannot be replaced in a binary without moving everything after it. Upstream avoids all of this by never having a second path. A stale tree from an interrupted run is cleared before the builder starts rather than at registration, and a failed build takes its partial output back out of the store.
- **New: `pkgs/linux/bootstrap/musl/gcc.nix`** - musl 1.2.6 compiled by gcc: the same C library as the tcc-built one, built the way its authors intended. gcc assembles everything tcc could not, so nothing is removed -- the complex math, the i386 and x86_64 assembly and `sigsetjmp` are all built -- and it is a shared library, with the dynamic loader and the `musl-gcc` wrapper the compilers above it link against. Verified: `musl-gcc` compiles a program that links dynamically against this musl and runs.
- **New: `pkgs/linux/bootstrap/gcc`** - GCC 4.6.4, compiled by tcc against musl: the last link, and a real C compiler with every byte behind it traced to the 181-byte hex0 seed. 4.6.4 because it is the newest gcc still written in C; later ones need a C++ compiler to build, which is what this one goes on to provide. gmp, mpfr and mpc are unpacked into the source tree, where gcc's build looks for them when there is no system copy. nixpkgs' `no-system-headers.patch` is not carried, and the option it goes with does not work here either: `--with-native-system-header-dir` does not exist in 4.6.4, and configure only warns at an option it does not know -- so with the patch applied and the option ignored, fixincludes read the host's `/usr/include`, copied glibc's `pthread.h` into `include-fixed`, and the libgcc the new compiler built stopped at a `bits/endian.h` musl does not have. nixpkgs gets away with it because a sandbox has no `/usr/include` to find. `NATIVE_SYSTEM_HEADER_DIR` is set to musl's headers directly instead, which is what the option would have done. Verified: it compiles a program using doubles, `long long`, structs by value and `snprintf`, linked by this bootstrap's own ld against this bootstrap's own musl, and it runs and returns the right answer.
- **New: `pkgs/linux/bootstrap/coreutils/musl.nix`** - GNU coreutils 9.10, compiled by tcc against musl. The 5.0 below it is built from live-bootstrap's makefile, which names the 62 programs it compiles -- and `env`, `uname`, `date` and `stat` are not among them. Nothing above noticed until gcc, whose libcpp configure runs its dependency-style probe through `env`: with no `env` every style fails and configure stops with "no usable dependency style found", which is not what it means.
- **New: `pkgs/linux/bootstrap/gnutar/musl.nix`** - the same tar 1.12 against musl, which restores modification times where the one below it does not. Built against Mes's C library, tar leaves every unpacked file with the extraction time in extraction order, so make reads a distributed `aclocal.m4` as older than the `configure.ac` beside it and reaches for an aclocal that is not in this bootstrap.

One edit, from nixpkgs: gnulib's `chdir_long` is compiled only when configure decides `PATH_MAX` is not a usable bound, and here it decides wrongly and leaves the call with nothing behind it.
- **New: `pkgs/linux/bootstrap/binutils`** - GNU binutils 2.46.0, compiled by tcc against musl: the assembler and linker gcc needs. tcc has its own of both and got the bootstrap this far on them, but gcc emits assembly only gas assembles and expects a linker that reads gnu ld's scripts. Two patches from nixpkgs, both about tcc: one makes ld's output deterministic, the other stops `ansidecl.h` from defining `__attribute__` away for a compiler that reports no gcc version, which took `aligned()` with it and failed an assertion in bfd's mmap window. Verified: gas assembles and ld links a program that runs.
- **tcc-musl links statically by default.** nixpkgs' `static-link.patch` as an edit rather than a patch file. There is no shared musl here, so a dynamically linked output names an interpreter that does not exist and the kernel refuses to run it -- and passing `-static` in `CC` is not enough, because a configure script or a libtool relink drops flags out of `CC` on the way to the final link. binutils is where that showed up: a gas and an ld that built cleanly and could not be executed.
- **New: `pkgs/linux/bootstrap/diffutils`** - GNU diffutils 3.8, compiled by tcc against musl: `cmp` and `diff`, which binutils' configure runs and gcc's build compares generated files with. The first package here that the Mes C library cannot carry at all -- its configure looks for `socklen_t` and stops when there is none -- and so the first built entirely on musl. - **New: `pkgs/linux/bootstrap/gawk`** - GNU awk, in two versions. Every autotools configure script uses awk, and a modern `config.status` writes a `subs.awk` with line continuations that 3.0.6 rejects -- so 3.0.6 (`mes.nix`, the newest awk the Mes C library can build) exists to build 5.3.2, which is the awk everything above uses.
- **New: `pkgs/linux/bootstrap/gnused/musl.nix`** - the same sed 4.0.9 compiled against musl instead of Mes's C library. Nothing in sed is wrong and nothing is patched: under the Mes C library, `getc` and `ungetc` on stdin do not agree with each other, so sed's `test_eof` reads a character, pushes it back, gets EOF, and `$` matches the first line of a pipe while `N` ends the script. A modern `config.status` pipes its substitution table through `sed '/^[^""]/{N;s/\n//}'`, which under that sed emits one line instead of the whole table, and every configure downstream then fails while creating its Makefile.
- **Fixed: musl is built twice, and `printf("%f")` prints the number.** The first musl is compiled by the tcc that still stands on the Mes C library, and that tcc miscompiles musl's `vfprintf`: every `%e`/`%f`/`%g` printed zero, however correct the arithmetic behind it was. Nothing above could format a float -- gawk's `printf "%d", 6*7` gave 0. Compiling musl again with the tcc that the first musl produced fixes it, which is the same argument tcc's own second round makes: a compiler that compiled itself is one whose output has been checked by the thing it produced. `tinycc-musl`'s `lib/` is now a complete `-B` directory as well, carrying musl's archives and crt objects beside `libtcc1.a`, because `-B` names one directory rather than a search path.
- **Cancellation is never spent as retry budget nor as cache fallthrough.** The retry classifier already re-threw asynchronous exceptions, but the per-cache catch-all one frame up converted every exception into a substitution error, so a Ctrl-C or timeout arriving mid-download was swallowed, the cache scan continued, and the build fell through to building locally instead of aborting. The sync/async split now lives in one shared helper used by the retry classifier, the per-cache attempt, and the builder's top-level catch-all: only synchronous exceptions convert into recoverable failures, and an interrupt propagates out of the whole operation.
- **`builtins.fetchGit` remembers a pinned revision.** A revision names one tree for all time, so re-cloning it on every evaluation is pure waste -- and worse than waste when the far end is down: a bootstrap pinned to a dozen revisions could not be built at all while one host answered 500s, though nothing about it had changed. A fetch of a pinned `rev` is now recorded under the user's cache directory and reused while the tree it names is still in the store. A bare `ref` is never cached, since it means "whatever this branch points at now". Evaluation's path READS also resolve through the store `--store` selected, which is what makes the recorded path findable at all.
- **Fixed: `libtcc1` is tinycc's runtime, not the C library's.** Every round of tcc was building `libtcc1` from Mes's `lib/libtcc1.c` -- a file of the same name meaning something else -- instead of from tinycc's own, beside the compiler being built. It is the compiler's runtime: the helpers tcc emits calls to for arithmetic the instruction set will not do in one step. Taking the wrong file is not a link error; the calls resolve to whatever else is around, and a cast from floating point to integer quietly produces zero. It also needs both of its sources, `libtcc1.c` and the architecture's second file (`va_list.c` in the fork, `alloca.S` in mainline). A fifth round of tcc is added along with it, matching nixpkgs' `tinycc-bootstrappable`, and `HAVE_SETJMP` is restored to rounds two and three, where it was dropped when the build script could only pass three options.

- **New: `pkgs/linux/bootstrap/stage0-posix`** - the full-source bootstrap, for Linux. The same shape as the Windows chain (which is a fork of this one): the 181-byte `hex0-seed` assembles `hex0_x86.hex0`, and the result is declared fixed-output at the seed's own sha256, so the seed reproducing itself is a build-time assertion rather than a claim. From there the chain walks upstream's `x86/mescc-tools-mini-kaem.kaem` one derivation per link - hex1, hex2, catm, M0, cc_x86, M2-Planet, blood-elf, M1, and finally a `hex2` built from C by the tools below it. kaem itself has no counterpart: nova-nix orders the links, which is all upstream needed a shell for. - **`--store` reaches evaluation, not just the builder.** A fetch during evaluation wrote to the platform store however the caller was invoked, so `--store DIR` could not be used at all where `/nix/store` is not writable - a multi-user Nix install, where it belongs to root. Evaluation now reads and writes under the store it was given; path identity is unchanged, still the canonical `/nix/store` spelling that hashes are computed over.
- **The builder resolves store paths through the configured store dir.** A derivation names its builder and arguments by identity (`/nix/store/...`), and the spawn boundary passed those through untouched. On Windows that worked by accident - a `/`-rooted path resolves against the current drive, so it found `C:\nix\store` when the process happened to be on C: - and on a Unix host with `--store` it could not work at all. The prefix is now rewritten to wherever the store actually is, and only when the two differ. Reference scanning is unaffected: it matches a path's hash, not the directory in front of it.
- **`pkgs/lib.nix` and `pkgs/build-support/` are shared.** `callPackageWith`, `makeScope` and `derivationWithMeta` are not Windows-specific, and now that there is a second package set they sit one level up rather than being reached for across it.
- **Per-store-path locks close the substitution race.** The streaming substituter deleted the destination before the first byte downloaded, with no lock and no validity re-check anywhere, so two processes sharing a store could interleave delete, materialize, and register into a valid database row pointing at deleted or torn bytes. Substitution now takes an exclusive lock on upstream's "\<store-path\>.lock" file - a raw write-access descriptor locked through filelock (flock on POSIX, LockFileEx on Windows; CC0-licensed, so nothing encumbers the Apache-2.0 distribution), because base's Handle-based locks cannot express this lock - before touching the destination, re-checks validity under the lock and adopts another process's finished path instead of deleting and redoing it (waiting on a busy lock is announced, as upstream does), and holds the lock across download, materialization, the on-disk recheck, and the caller's registration transaction, releasing it on every exit path. The protocol is upstream C++ Nix's pathlocks mechanism (src/libstore/pathlocks.cc and the substitution path in local-store.cc) exactly. One deliberate divergence, documented in Nix.Store.Lock: lock files persist instead of being marked and deleted, which removes upstream's deleted-lock-file hazard outright and needs no separate Windows path.

- **store delete joins the per-path lock protocol, and lock files are not delete targets.** The delete command ran its unregister-and-remove sequence with no lock, so a delete racing another process's substitution of the same path could remove the freshly materialized tree between the substituter's on-disk recheck and its registration commit - the exact valid-row-pointing-at-deleted-bytes race the locks close, reopened through the other door. Deletion now holds the target's path lock across the whole sequence, blocking (with the announced wait) while a substituter holds it, as upstream's deletePath does. A target naming a lock file is refused with the reason: lock files are never deleted here by design, and removing one would reopen the deleted-lock-file hazard that design removes. Names like flake.lock are legal store-path names, so the refusal consults the registration rows: only an unregistered file whose suffix-stripped name is a well-formed store basename reads as a lock file, and a registered object of the same shape deletes normally.

- **zstd, both directions: substitution accepts it, push can produce it.** The modern caches (Cachix, attic, FlakeHub) serve NARs zstd-compressed; both decompression paths - streaming and the strict oracle - now speak it through nova-cache 0.10's zstandard sublibrary, bounded by the declared NarSize like xz (the strict decompressor's resolved function moves into IO: the zstd binding's decoder is IO-native, and the shape follows the codecs). Push gains --compression none|zstd, a property of the destination cache as upstream models it - none stays the default so existing cache content stays uniform - with the compressed object named by its own file hash and the narinfo's file fields describing it. The bound rises to nova-cache 0.10 with the zstandard sublibrary and the pinned index-state advances past the release. (#111)
- **Substitution failures carry a retry class, and every failure path cleans up.** Exceptions thrown mid-stream - a dropped connection, a full disk - previously escaped both the retry budget and the partial-tree cleanup, so the single most common transient failure never retried and could orphan an unverified tree at the store path. Every attempt now converts synchronous exceptions into the pipeline's failure channel (asynchronous cancellation re-throws untouched) and removes the tree on every exit. Failures classify explicitly, matching upstream's transfer layer: transport errors, torn transfers, and truncation retry with backoff; a completed transfer that verifies wrong, a body past its ceiling, or a 4xx fails at once, since retrying a deterministic failure only delays the local-build fallback.
- **The NAR download cap derives from the signed NarSize.** The compressed-body cap was keyed to the narinfo's FileSize, which the Ed25519 fingerprint does not cover, so a rewritten FileSize on a validly-signed narinfo could buy an unbounded download. The cap is now a ceiling computed from the signed NarSize plus a small framing-overhead margin, and the unsigned FileSize may only lower it, never raise it. Caches that omit FileSize (on-the-fly compressors) gain the same margin, so incompressible NARs whose compressed body slightly exceeds NarSize substitute where they previously aborted.
- **An empty Compression field means bzip2, never identity.** Upstream decodes an absent or empty Compression as bzip2, the field's historical default, and nova-cache's parser matches that coercion; treating the empty string as identity diverged from it. The compression vocabulary now lives in one register (Nix.Compression) parsed once at the narinfo boundary, so the streaming and strict dispatch cannot drift.
- **Substitution streams: download, decompress, hash, parse, and unpack in one bounded pass.** The substituter realized every NAR in memory before touching disk - an RSS spike the size of the path being fetched, documented in place since the first cut. The pipeline now drives nova-cache's streaming pieces end to end: the HTTP body feeds the bounded xz source, the incremental hash, the chunk-fed NAR parser, and a new streaming store sink that materializes events as they arrive, so memory is bounded by decoder buffers and the parser's structural-string cap, never by archive or file size. Disk writes therefore begin before the hash can be known - upstream's ordering exactly - and any failure or mismatch removes the tree it wrote; the on-disk recheck streams too. One divergence, documented at the sink: sibling names colliding on a folding filesystem always take upstream's case-hack renaming, never the NTFS true-name path, which can only be enabled on an empty directory the stream cannot pre-scan. (#107)
- **Substitution from cache.nixos.org works: xz NARs decompress.** The default cache serves every NAR xz-compressed, and decompressorFor rejected the value up front, so the shipped configuration could never substitute a single path. nova-cache 0.9's bounded decoder is wired in via its public nova-cache:xz sublibrary - an ordinary solver-visible dependency, no flags on either side; the bound rises to >= 0.9 && < 0.10 and the pinned index-state advances past the release - with output capped at the narinfo's signed NarSize and decoder memory at nova-cache's default, so a hostile stream expands to nothing the narinfo did not promise. Unsupported compression values still reject before any download is paid for. Verified against production data: recorded cache.nixos.org narinfos parse, validate, and signature-verify offline in the suite, and a real path substitutes end to end from the live cache. (#27)
- **nova-cache 0.8.0.0.** The bound rises to >= 0.8 && < 0.9 and the pinned index-state advances past the release. NAR parsing now rejects the full Windows reserved-device set at the parse boundary - COM0/LPT0, space-padded device stems ("NUL .txt"), and the superscript-digit forms - the same names materialization already refused, so the refusal moves earlier and the two guards agree. 0.8 also brings the streaming NAR interface and the NarSize-bounded xz decoder that foreign-cache substitution builds on next.
- **builtin:unpack resolves srcs through the store dir.** The srcs env value carries eval's canonical /nix/store spelling; unpack opened it verbatim, and on Windows a bare /-rooted path resolves against the current drive - the build worked only when the process happened to run from C:. Found by the e2e job's first flights (#100) on GitHub's D:-workspace runners. Each srcs entry now parses as a store path and renders through the configured store dir (the identity on Unix), a non-store-path entry fails loudly, and the e2e job no longer pins its working directory. (#101)
- **Toolchain: GHC 9.14.1 (the first GHC LTS release)** - CI, the release pipeline, and the README badge move from GHC 9.8.4 to 9.14.1. GHC 9.14 opens GHC's new LTS scheme (a minimum of two years of bugfix releases), and under that scheme every earlier series stops receiving fixes, so no version in between had a future. Dependency bounds already admitted the newer compiler and the full set resolves on it. The project targets the LTS alone: base >= 4.22, and foldl' comes from the Prelude, so its eleven redundant Data.List imports are gone. The deprecated pattern namespace specifier stays for now - hlint cannot yet parse the data replacement GHC suggests - with its deprecation warning muted in the cabal file until hlint learns the new spelling.
- **`builtins.fetchGit` fetches a pinned revision, not just a branch tip** - `rev`, `ref`, `submodules` and `shallow` are all now read from the argument set, `git fetch`/`checkout` replace the old unconditional `--depth 1` clone, and the result is the same attrset upstream's returns: `outPath`, `rev`, `shortRev`, `revCount`, `narHash`, `lastModified`, `lastModifiedDate` and `submodules`, all read from the clone before its (and every submodule's) `.git` metadata is stripped and it is copied to the store. Checked against a real Nix on the same two repositories: identical `outPath`, `narHash`, and every other field, submodule fetches included.
- **Fix: the executable bit survives on Windows** - a NAR records whether each regular file is executable, and a store path's identity is the hash of that. Windows has no such bit: `getPermissions` answers from the file's *extension* there, so a checked-out `configure` serialised as non-executable and a tracked `foo.exe` as executable, whatever either one was. This was not cosmetic - the substituter unpacks a downloaded NAR and requires the tree to reproduce the declared hash, so any cached path holding an executable without an executable extension was downloaded, rejected, and deleted. The bit now lives in an NTFS alternate data stream (`:nova.exec`) whose presence *is* the bit: addressable through ordinary file IO, invisible to directory listing, removed with the file. `builtins.fetchGit` sets the marks from git's index (`100755`), the only place a checkout records them, before `.git` is stripped. Measured: the GNU Mes tree - 60 executable files - now hashes to the same store path on Linux and Windows, and a NAR round-trip that differed before now matches. On Unix the whole thing is the mode bit and nothing changes.
- **New: `pkgs/windows/bootstrap/mes`** - GNU Mes as a PE32 executable, and the first thing this bootstrap builds with the toolchain it just produced rather than assembles by hand: M2-Planet compiles Mes's C to M1, M1 assembles it, and the C `hex2` links it against the PE header and the ntdll plumbing -- all three being `stage0`'s own output. A translation of Mes's `kaem.windows.run`, the way `mescc-tools-boot.nix` translates stage0-pe32's `mescc-tools-mini.cmd`; `configure`'s one generated input (`include/mes/config.h`, two lines for a non-system libc) is a `builtins.toFile` rather than a shell run, so the bootstrap still needs no shell. Verified on Windows 11: `mes-m2.exe` runs Mes's own `boot.test` (14 assertions), `macro.test` (7) and `base.test` (41) with no failures, and the binary built by the PE32 chain behaves identically to the reference one upstream builds with GNU/Linux M2-Planet\/M1\/hex2.
- **Fix: `builtins.toFile` outputs are registered** - `writeToStore` wrote the file to its content-addressed path during evaluation but nothing ever registered it, so any derivation naming a `toFile` output failed with `registerPaths: ... references unregistered path`. Registration needs the store DB, which only the build driver holds, so the path is recorded during evaluation and registered before the build, the way `materializeEvalSources` already handles path literals. The write is also idempotent now: the path *is* the hash of the bytes, so an existing file already holds them, and rewriting a registered path fails outright once it is read-only.
- **Removed: `pkgs/windows/bootstrap/hello.nix`** - the hand-written proof that the stage-0 MinGW-w64 seed could build something, superseded once `by-name/he/hello` built the same GNU hello through the real stdenv. `pkgs/windows/hello.nix` now points `nova-nix build` at that package instead.
- **The bootstrap follows the nixpkgs layout for bootstraps** - `pkgs/windows/bootstrap/stage0-pe32` is now shaped like nixpkgs' `pkgs/os-specific/linux/minimal-bootstrap/stage0-posix`: a `default.nix` that builds a scope, a `platforms.nix` holding the arch-dependent names, a `bootstrap-sources.nix` pinning the upstream source, a `hex0.nix` that turns the seed into a checked `hex0`, and a `mescc-tools-boot.nix` that walks the chain from `hex1` through `hex2-new` (M2-Planet, the first C the chain compiles rather than hand-assembles, standing on M2libc's `bootstrappable.c` and a Windows port of its `bootstrap.c`, both git submodules pulled in by the same `fetchGit { submodules = true; }` that fetches everything else). Nothing is vendored any more: the chain's sources and its seed are fetched from [stage0-pe32](https://github.com/Pandapip1/stage0-pe32), pinned by one revision, so the bootstrap is audited by reading upstream rather than by diffing copies of it. `lib.makeScope` replaces `lib.packagesFromDirectoryRecursive`, and the `assembleHex`/`concatHex` builders fold into the `run` helper the chain shares with nixpkgs'. Every link now carries a `meta`, via a `derivationWithMeta` that keeps it out of the builder's environment so a description cannot change a store path. Above `M2` the chain stops hand-assembling entirely: `M1` (mescc-tools' `M1-macro`, a fuller assembler than `M0` -- more label and pointer widths, several architectures in one binary) and `hex2-new` (mescc-tools' `hex2`, which unlike the hand-written one is not limited to a fixed label table) are both compiled by `M2` from upstream's own C. `hex2-new` needs a real preprocessor, so it drops `--bootstrap-mode` and stands on the full M2libc -- `stdio.c`'s `FILE` and its buffering over a Windows POSIX layer -- rather than the single `bootstrap.c` everything below it uses. That POSIX layer is C rather than assembly: `ntdll.c` hands compiled C a resolved ntdll routine by slot, so a syscall no longer needs a hand-written M1 stub apiece, and its slot numbers are generated from the same list `ntdll-i386.hex2` resolves so the two cannot drift. Which C library a link gets is now a file catm picks -- `_start` calls `:__libc_init`, and `libc-bootstrap.M1` defines it as a no-op while `libc-full.M1` defines it as `__init_malloc` plus `__init_io`. `hex2-new` takes the latter, without which M2libc's `stdin`/`stdout`/`stderr` globals stay NULL and every error path faults inside `fputs` instead of printing (measured: `hex2-new --version` faulted with `0xC0000005` before, prints `hex2 1.7.0` after). `process.c` completes that layer with `__spawn`, `waitpid` and `execve`; `fork` returns -1 and says why, because its meaning is that the child returns from the same call with the same memory and Windows has no call that does that, so fork-exec-wait is taken apart into the steps Windows can do. Every PE32 executable in the chain now gets a store path ending in `.exe`, so it can be run directly.
- **New: `hex2`** - the third link of the chain, assembled by `hex1`. It adds multi-character labels and five pointer forms: `!name`/`@name`/`%name` are one, two and four byte displacements, `$name`/`&name` are two and four byte absolute addresses, and `!name>base` measures the displacement from a named base rather than from the pointer. `ip` counts from the image base, so a label's value is the address it will have once loaded and an absolute pointer needs no adjustment. The label table is reserved past the end of the file and zero-filled by the loader, costing nothing in the source.
- **New: `hex1`** - the second link of the bootstrap chain, assembled by `hex0`. It adds single-character labels (`:X`) and four-byte relative pointers to them (`%X`), so a jump's displacement is computed rather than counted by hand. Because a label may be referred to before it is defined, the input is read twice with a rewind between the passes -- `NtSetInformationFile` with `FilePositionInformation`, the NT equivalent of upstream's `lseek`. Labels live in a flat 256-slot table indexed by the character itself, as upstream does.
- **New: `pkgs/windows/bootstrap/stage0-pe32`** - the start of a full-source bootstrap. `hex0-seed.exe` is a 1623-byte PE32 seed that reads hexadecimal digit pairs and writes the bytes they denote, with the same contract as upstream stage0's hex0 (`argv[1]` in, `argv[2]` out, `#` and `;` comments). It imports nothing: `NumberOfRvaAndSizes` is 0, and it locates ntdll through the PEB and resolves `NtCreateFile`/`NtReadFile`/`NtWriteFile`/`NtClose`/`NtTerminateProcess`/`RtlDosPathNameToNtPathName_U` from the export table by name. `hex0_x86.hex0` is its annotated source; assembling it reproduces the binary byte for byte, and the `hex0` package *is* that self-assembly, declared fixed-output so the round-trip is a build-time assertion rather than a claim in a comment. Because each link is a derivation, nova-nix orders the chain itself and upstream's `kaem` shell has no counterpart.
- **`builtins.placeholder` is substituted at build time** - the sentinel is replaced in a derivation's `args` and environment values with the same path `$out` carries. A builder that takes its destination as an argument rather than reading the environment (`hex0 input output`) can now be driven directly.
- **The package set is a fixpoint** - `pkgs/windows/lib.nix` adds `callPackageWith` and `makeScope`, modelled on nixpkgs' `lib.customisation`. A package now declares its dependencies as formal parameters (`{ stdenv, zlib }: ...`) and callPackage supplies them from the set, instead of each recipe reaching across the tree with a relative import. The bootstrap chain gets a scope layered over the top level, so a link can name the link below it (`hex1` is built by `hex0`) without those names reaching the top.
- **`pkgs/windows` follows the nixpkgs layout** - packages moved to `by-name/<shard>/<pname>/package.nix` (shard = the pname's first two characters), the stdenv machinery to `stdenv/`, and the sha256-pinned MSYS2 seeds plus the raw-derivation bootstrap proof to `bootstrap/`. `pkgs/windows/default.nix` discovers `by-name` with `builtins.readDir`, so adding a package is adding a directory. No recipe changed beyond its import paths.

### Milestone: A Stage-1 stdenv That Builds Real Software

nova-nix now builds real third-party software from source on Windows through a small stage-1 stdenv. A package is `{ name; src; buildInputs; }`, and a `setup.sh` genericBuild drives unpack, configure, build, install, and a fixup that makes outputs standalone - proven on GNU hello, GNU sed, and zlib plus a program that links it.

## 0.5.0.0 - 2026-06-11

### Milestone: Push and Pull Against a Binary Cache

A native Windows build can now publish its outputs to a binary cache and substitute them back on another machine. The toolchain seed and the `hello` build push to `cache.novavero.ai` with `nova-nix push`, and a fresh store realizes them by signed download instead of rebuilding.

## 0.2.0.0 - 2026-06-05

### Milestone: `import <nixpkgs> {}` Evaluates

- **`import <nixpkgs> {}` now evaluates to WHNF** - the top-level package set resolves and enumerates ~23,000 attributes, and a package evaluates through the full stdenv bootstrap down to a derivation: `(import <nixpkgs> {}).hello.drvPath` yields a `/nix/store/...-hello-2.12.1.drv` path. ## 0.1.9.0 - 2026-06-05

### nixpkgs Evaluation: Lazy Derivations

- **Fix: `import <nixpkgs> {}` infinite recursion - lazy `derivation` over `derivationStrict`** - `builtins.derivation` was eager: forcing a derivation to WHNF forced its entire env/input closure. ## 0.1.6.0 - 2026-02-26

### De Bruijn-Style Positional Env + SmallArray Slots

- **De Bruijn-style variable resolution** - New `Nix.Expr.Resolve` pass replaces `EVar` with `EResolvedVar level index` for lambda-bound variables. Called at parse time; all subsequent evaluation uses positional indices instead of name-based `Map` lookups.
- **Array-based Env** - `envSlots :: SmallArray Thunk` replaces `envBindings :: Map Text Thunk`. Lambda formals get O(1) positional indexing via `indexSmallArray` instead of O(log n) `Map.lookup`. Let/rec bindings and builtins remain in name-based `envLazyScope` (already zero Map.Bin overhead).
- **Scope chain** - `Env` uses parent pointer chain instead of `Map.union`. Variable lookup walks the chain: positional slots, then `envLazyScope`, then parent, then with-scopes. Avoids O(n) `Map.union` when extending large envs.
- **Inherit desugaring** - `inherit x;` is desugared to `x = x;` in the resolution pass so inherited lambda formals resolve to `EResolvedVar` (lambda slots have no names at runtime).
- **Heap savings** - Eliminates 29.9M Map.Bin nodes (1.37 GB) from lambda formals. Replaced by SmallArray (one heap object per env, O(1) index) + scope chain parent pointers.
- `primitive` dependency added for `Data.Primitive.SmallArray`
