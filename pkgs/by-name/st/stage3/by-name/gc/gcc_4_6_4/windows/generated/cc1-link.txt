# 4. The 8 C99 _Complex libgcc2.c lib2funcs tcc can't compile
#    (__mulsc3/__muldc3/__mulxc3/__multc3/__divsc3/__divdc3/__divxc3/__divtc3):
#    grepped for callers across the ENTIRE closed source set this package
#    actually builds (gcc/*.c, gcc/c-family/*.c, gmp-4.3.2/*.c,
#    mpfr-2.4.2/*.c, mpc/src/*.c) -- zero references to any of the eight
#    symbol names anywhere. The one place complex host arithmetic exists at
#    all in this closure -- mpc/src/get_x.c's mpc_get_dc/mpc_get_ldc and
#    set_x.c's mpc_set_dc/mpc_set_ldc, real uses of C's `double _Complex`
#    type doing genuine complex multiply/add (`I * im + re`) -- are
#    themselves never called by gcc's own source (grepped gcc/*.c gcc/*.h
#    for mpc_get_dc/mpc_set_dc/mpc_get_ldc/mpc_set_ldc: zero matches; GCC's
#    real/complex constant folding goes through mpc_mul/mpc_div on
#    mpc_srcptr, pure GMP/MPFR, never through C's native _Complex type at
#    all). Since a static-archive member is only pulled into the link when
#    one of its symbols is referenced, get_x.o/set_x.o never even get
#    linked into anything cc1 needs -- so it does not matter, for THIS
#    bootstrap, whether tcc's own `I * double` codegen would want a
#    __muldc3 call or not; the code path is unreachable from cc1's actual
#    call graph. Confirmed dead code for the host side, same category as
#    ../binutils's own confirmed-dead-code exclusions.
#
#    Verdict: exclude all 8 from libgcc's L_* file list (LIB2FUNCS_EXCLUDE
#    at the build.kaem level, matching gcc's own Makefile.in variable name)
#    with this file cited as the reference for why -- target C programs
#    built by this bootstrap's gcc.exe that use C99 _Complex multiply/
#    divide will fail to link (undefined __muldc3 etc.), which is an
#    accepted, documented gap, not an oversight. Nothing in gcc/gmp/mpfr/
